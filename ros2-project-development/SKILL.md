# ROS 2 项目规范开发

目标：从项目创建之初就明确功能边界、工作空间布局和可部署方式，让功能包能独立使用、系统能组合启动，换目录或设备后仍可按说明复现。围绕当前需求做工程决定，不为凑目录或抽象而增加功能。

## 使用顺序

1. **明确需求与边界**：确认 ROS 2 发行版、操作系统和目标架构、功能、输入输出、运行设备、现有约束与预期验收。区分新建项目和已有项目；已有项目先了解真实结构、接口、启动方式与行为，保留已有数据和用户修改，再有针对性地调整。
2. **先设计工作空间和功能包**：新项目从一开始在工作空间 `src/` 下建立边界清晰的功能包；工作空间内使用 `build/`、`install/`、`log/` 放构建、安装和日志产物。按功能划分基础包；只有存在真实组合需求时才建立系统组合包。参考 [工作空间与功能包](references/workspace-packages.md)。
3. **先定义模块契约，再实现**：写清每个模块的职责、节点入口、话题/服务/动作、消息类型、参数、输入输出、单位、失败及就绪行为；尽量复用标准消息。确有跨包共享需要时再设计自定义接口包。
4. **各包独立实现，系统包负责组合**：基础能力应能脱离系统总成单独启动和测试。系统组合包通过 launch 启动基础节点；运行时的状态协调及业务流程由组合包内的协调节点承担，不复制基础模块实现；新增组合需求优先在组合层完成。业务确实需要的独立功能才新增基础包。
5. **实现可安装、可迁移的资源和依赖**：路径通过包 share、参数和相对路径解析，不写绑定用户名、当前工作目录或特定机器的绝对路径。资源由所属功能包管理并正确安装；大型权重等可以由明确的下载/外部资源方案准备，禁止假定复制虚拟环境即可迁移。参见 [资源、路径与依赖](references/paths-dependencies.md)。
6. **做好运行行为**：新项目如使用模型，默认对实际启用且支持的模型做可配置的无副作用预热，在各依赖就绪后明确提示系统可用；资源不允许、模型不适合或用户另有要求时说明原因。迁移已有项目保留既有默认行为，除非用户要求改变。控制日志噪声；退出时回收节点、子进程和占用的设备。参见 [通信与系统组合](references/integration-lifecycle.md)。
7. **编译、验证并写可执行文档**：按改动范围验证独立模块和集成链路，涉及设备时说明回放、仿真和实测的边界。根 README 给清晰的依赖、构建和启动入口；每个功能包保留一份完整 README，解释实际目录、include 内容、参数及独立使用方式。按 [交付与验收](references/delivery-acceptance.md) 验证说明中的命令。

## 不可省略的工程判断

- 不把用户的目录偏好误称为 ROS 2 唯一合法布局。新建项目按用户偏好将节点入口源码放包内 `src/`；已有项目尊重原结构，除非用户要求调整。可复用代码及头文件遵照项目约定，C++ 公共头文件通常用 `include/<包名>/`，Python 导入包要按打包机制正确安装。用户要求将共享实现放 `include/` 时，要同时保证 Python 包能安装和导入。配置在 `config/`，launch 在 `launch/`；按需创建目录，不强制每个包拥有所有目录。
- 不把 `install/` 当唯一源码或唯一资产来源；`build/`、`install/`、`log/` 可重建，用户数据和外部模型不可因此视为可删除。遵循项目要求将配置、小型资源和模型清单放在所属包的 `include/` 或 `config/`，由安装规则部署到包 share；对大模型、许可限制资源使用可配置外部路径或可验证下载，不把权重强制提交仓库。
- `requirements.txt` 是 pip 可执行的 Python 依赖清单；ROS/系统依赖由 `package.xml`、rosdep 与系统安装说明共同覆盖。确认 Python 解释器、ROS Python 绑定与依赖实际处于同一可用环境，运行时能找到它们。已有版本未验证时不要写成测试通过。
- 与硬件、运动或外部服务有关的副作用按用户授权和设备实际状态控制。安全策略清晰、可说明；不擅自新增隐藏的开机自启或改变既有默认行为。停止、取消、失败和到位等状态应如实区分。
- 迁移或清理已有项目时先厘清依赖和现有行为，保证接口、参数、资源及启动入口迁移后仍正确；测试通过也不代表有权删除数据或历史文件。按用户明确授权处理。
- 不把模型加载、构建、软件回放或仿真成功说成实机验收。速度和资源占用仅引用有条件、有指标的实测记录，不能用估算填充缺失数据。
